# 기출문제 연습프로그램 설계 문서

## 1. 시스템 개요
- 목표: PDF 기출문제와 정답 텍스트를 입력받아 오프라인에서 문제 연습을 지원하는 단일 사용자 MAUI 앱을 제공한다.
- 지원 플랫폼: 데스크톱 및 모바일
- 저장 방식: 로컬 저장소(JSON 파일 기반, 추후 SQLite 전환 검토)

## 2. 기능 요구사항
### 2.1 필수 기능
- 카테고리 단위 문제 묶음 관리
- PDF 업로드(이미지 기반 분석) 및 문제 분리
  - OCR 텍스트와 페이지 이미지를 저장
  - 문항 번호 헤더, 예상 문항 범위, 진단 결과를 기준으로 문항 후보를 생성
- 정답 파일 업로드 및 매핑
  - 정답 형식: `문항번호:정답` 또는 `문항번호:정답1|정답2`
  - 정답 파일이 비어있어도 문항 후보는 `정답 미매핑` 상태로 저장 가능
  - 동일 파일에 대해 정답 파일만 다시 업로드해 정답만 갱신/매핑 가능
    - 부분 정답맵은 지정한 문항만 갱신하고 미지정 문항의 기존 정답/유형을 유지
    - 명시적 빈 매핑(`2:`)만 해당 문항의 정답을 해제
  - 정답맵 파싱 오류, OCR 후보 없음, 후보 밖 정답 번호, 문항 번호 중복/리셋 등 구조 오류가 있으면 저장 차단
  - 정답만 순서대로 나열한 형태(`1,2,3`) 지원
    - 문항 번호는 입력 순서로 `1번,2번,3번...` 자동 매핑
    - 빈 항목은 해당 문항의 정답 미등록 상태로 저장
  - 객관식은 숫자 정답을 기반으로 채점
- 연습 실행
  - 카테고리 선택 후 출제 개수 지정
  - 최대 출제 개수는 카테고리 등록 문항 수로 제한 표시
  - 랜덤 출제
- 즉시 채점
  - 객관식: 사용자 입력은 숫자 한 개, 정답 후보 집합 중 하나와 일치 시 정답
  - 채점과 오답 저장이 완료될 때까지 입력/이동을 잠그고, 결과를 현재 문항에 표시한 뒤 사용자 요청으로 다음 문항 이동
- 주관식: 입력값의 모든 공백을 제거한 뒤 대소문자 정규화(영문 Upper)
- 결과 표시
  - 채점 가능한 문제 수 대비 정답 개수와 정답 미등록 `미채점` 수를 분리 표시
- 오답 문제 모음
  - 오답만 조회
  - 재도전 시 정답이면 오답 목록에서 삭제
  - 사용자 수동 삭제 가능
- 로컬 저장소 복구
  - JSON 저장소 파싱 실패 또는 0바이트 파일은 고유 이름으로 손상 파일을 백업한 뒤 정상 빈 상태 파일을 기록
  - 손상 파일 백업에 실패하면 원본을 보존하고 복구·후속 쓰기를 중단해 데이터 손실을 방지
  - 저장 경로별 프로세스 공유 잠금과 고유 임시 파일, 디스크 flush, 원자 교체를 적용
  - 전체 덮어쓰기 시 동일 `(카테고리, 원본 파일, 문항 번호)`의 ID와 오답 이력을 유지하고 사라진 문항만 정리

### 2.2 제약/정책
- OCR 품질이 매우 낮으면 해당 PDF는 처리 불가로 표시
- OCR 추출은 플랫폼 공통 인터페이스로 처리한다. 플랫폼별 렌더링/OCR 어댑터를 사용한다.
  - Windows: 플랫폼 PDF 렌더러와 Windows OCR 엔진 사용
  - Android: `PdfRenderer`와 한국어 ML Kit 텍스트 인식기 사용. 별도 CLI 도구나 네트워크 연결이 필요하지 않음
    - 해시 계산, 렌더링, PNG 압축, ML Kit 처리는 UI 스레드 밖에서 실행
    - .NET 취소 요청이 네이티브 ML Kit 작업을 즉시 중단할 수 없으므로 작업 완료까지 리소스를 유지한 뒤 취소를 확정
  - Mac Catalyst/macOS: 번들/패키지 또는 PATH에서 `pdftoppm`, `tesseract`를 탐색하며 TSV 결과로 텍스트·행 좌표·신뢰도를 추출
  - iOS: 외부 명령행 도구 실행이 제한되므로 현재 OCR 분석 미지원, 플랫폼 전용 OCR 어댑터 구현 필요
  - 운영체제별 OCR 경로는 공통 인터페이스(`IPdfAnalysisService`)에서 분기하며, Mac Catalyst용 명령행 도구는 `Tools*` 디렉터리(`Tools`, `Tools/mac`)에서도 탐색
  - 렌더링/OCR 캐시는 PDF 내용 해시별 디렉터리로 분리하고, 콘텐츠별 잠금과 검증된 PNG의 원자 게시를 적용하며 기존 결과를 일괄 삭제하지 않음
  - 모든 번호 형식의 헤더 가설을 먼저 보존하고 번호 연속성, 형식 일관성, 열 내 정렬, 질문 문맥을 함께 평가해 문서 단위 경로를 선택
  - 선택지와 문항 경계가 경쟁하거나 동일 번호의 강한 후보가 복수이거나 한 물리 OCR 행에 복수 헤더가 있어 좌표를 분리할 수 없으면 `ambiguous-boundary` 구조 오류로 저장 차단
  - 원형 문자·영문·닫는 괄호처럼 선택지에도 흔한 번호 형식만 이어지면 질문형 문구가 있어도 문항열로 확정하지 않으며, 질문 근거가 분명한 단일 점 헤더는 보존
  - 후속 페이지의 선행 텍스트는 이전 문항의 연속 지문으로 유지하고, 번호 없는 질문 문장을 누락 번호로 생성하지 않음
  - 명시된 공통 지문은 이전 문항에서 분리한 별도 영역으로 관리하고 대상 번호 범위의 문항에 공유. 범위 없는 문구는 첫 문항 앞에서만 자동 공유
  - 문항 이미지 경계는 OCR 텍스트 bbox가 아니라 페이지·열 band와 다음 확정 헤더의 단일 공유 경계를 사용하며, 같은 페이지의 열 전환도 복수 이미지 조각으로 표현
  - 합성·누락·겹침 OCR 좌표, 3단·문항 중간 전폭 영역처럼 안전하게 표현할 수 없는 배치, 빈 이미지 영역, 문항 또는 공통 지문과 겹치는 이미지 영역은 추정 크롭으로 대체하지 않고 구조 오류로 저장 차단
  - 문항 번호가 시작 번호로 재설정되는 합본 PDF는 중복 진단으로 저장을 차단
  - 분석 취소는 OCR/진단 저장 단계까지 허용하고, 검증된 문항의 저장 커밋이 시작되면 취소를 잠금
- 동일 파일명 업로드 시 덮어쓰기 동의 확인 후 진행. 확인 UI를 사용할 수 없으면 자동 승인하지 않고 중단
- 기존 동일 소스에 덮어쓰기를 적용하지 않는 경로는 answer-only update로 취급한다. 기존 번호의 구조와 ID를 유지하고 지정 정답만 갱신하며, 새로 검출된 번호의 crop을 기존 집합에 혼합하지 않는다.
- 원본 PDF 등록은 같은 폴더의 고유 임시 파일에 완전히 기록·flush·헤더 검증 후 원자 교체
- 분석 실행 중에는 카테고리·파일·예상 범위·정답맵·덮어쓰기 입력을 잠그고, 실행 시작 시점의 스냅샷과 화면 컨텍스트를 일치시킨다.
- OCR 완료, 구조 검증, 저장, 화면 갱신을 별도 상태로 표시하며 최종 성공·취소·구조 실패 상태를 진행 중 문구와 구분한다.
- 구조 검증 실패로 문항 저장이 차단되어도 최근 진단은 현재 분석 화면에서 열 수 있어야 한다.
- 실패·취소된 동일 파일명 재분석은 `latest-attempt`, 실제 반영된 분석/진단은 `committed` 파일로 분리한다. 저장 문항 검토 화면은 `committed` 진단만 읽고, 이는 실제 문항 이미지 경계를 새로 반영한 커밋에서만 갱신한다.
- 레이아웃은 `DeviceIdiom`만으로 고정하지 않고 실제 페이지 폭을 기준으로 1열/2열과 이미지 viewport를 다시 계산한다.
- 연습 화면의 세로 이동은 단일 스크롤이 소유하며, 창 크기 변경은 debounce 후 마지막 크기만 반영한다.
- 문항 전환 시 이미지 확대율과 스크롤 시작점, 답 입력 포커스와 스크린리더 안내를 복구한다. 핀치의 상대 배율은 누적하고, 진행 중에는 이미지 소스를 재생성하지 않고 시각 변환만 적용한 뒤 완료 시 한 번 확정한다.
- 저장 PNG는 signature와 chunk 경계, CRC, `IHDR`/`IDAT`/`IEND` 완결성을 검증한다. 이미지 조각이 일부라도 누락·손상되면 경고를 표시하고, 전부 열 수 없을 때는 OCR 텍스트를 대체 표시한다.
- 카테고리 및 등록 문항 CRUD, 정답 파일 선택은 공통 구조 변경 잠금을 사용해 분석·가져오기와 교차 실행하지 않는다.
- 사용자는 진행 중인 연습을 확인 후 종료할 수 있고 이미 반영된 오답 기록은 유지한다.
- 오프라인 필수 동작
- 원본 PDF, OCR 결과, 학습 이력은 Android 자동 백업 대상에서 제외
- 단일 사용자

### 2.3 광고 기능(선택)
- 현재 앱 코드에는 광고 SDK와 광고 권한을 넣지 않는다. 광고 기능을 실제 구현하는 시점에만 아래 설계를 적용한다.
- 대상 플랫폼: Android / iOS 모바일 앱 모두
- 목적: 앱 실행 화면에 광고(예: 배너/전면광고)를 노출할 수 있는 구조를 확보
- 우선 채택 방식: MAUI용 AdMob 플러그인(`Plugin.MauiMTAdmob`) 기반으로 우선 구현
- 운영 모드에서는 실 광고 단위 ID 사용, 개발·테스트 단계는 테스트 광고 ID 사용
- 사용자 동의가 필요한 지역(예: EEA/US ATT 정책 적용 국가)은 동의 플로우를 별도 처리
- 광고 실패 시에도 핵심 문제풀이 기능은 정상 동작해야 함(광고 의존 제거)

### 2.4 광고 연동 설계(안)
- 구성 원칙
  - Android/iOS 각각 앱 ID와 광고 단위 ID를 분리 관리
  - 앱 시작 시 광고 SDK 초기화, 연습 화면에서 배너 노출, 필요 시 전면광고 노출
  - 실패/미지원 기기에서는 광고가 없어도 앱 동작 유지

- 플랫폼별 반영 파일(단일 프로젝트 구조 기준)
  - Android: `Platforms/Android/AndroidManifest.xml`
    - 광고를 구현하기 전까지는 인터넷/네트워크 상태 권한을 요청하지 않음
    - `com.google.android.gms.ads.APPLICATION_ID` 메타데이터 등록
    - 필요 시 AdMob `AdActivity` 관련 manifest 속성 검토
  - iOS: `Platforms/iOS/Info.plist`
    - `GADApplicationIdentifier` 등록
    - `SKAdNetworkItems` 및 광고 관련 식별자 검토/등록

- MAUI 초기화 흐름(요약)
  - `MauiProgram`에서 플러그인 초기화 호출
  - 광고 화면(예: 연습 화면 하단)에 배너 뷰 배치
  - 광고 단위별 노출 주기 제한(연타 클릭/중복 노출 방지) 정책을 명시적으로 적용

- 검증 및 배포 고려사항
  - Android: 실제 기기/에뮬레이터에서 테스트 광고가 정상 노출되는지 확인
  - iOS: Xcode 기반 빌드 환경에서 `Info.plist` 반영 상태와 광고 초기화 동작을 확인
  - 정책/심사: 스토어 정책 및 AdMob 가이드라인(개인정보/동의/트래킹) 준수

- 미확정/확실하지 않음
  - MAUI 공식 광고 통합 방식은 버전별/플러그인별로 상이할 수 있어 대상 SDK 버전 호환성은 적용 직전에 재확인 필요

## 3. 정답 규칙
- `MultipleChoice`(객관식): 문자열을 `:` 기준으로 정답을 파싱하여 숫자 배열로 저장
- 정답이 여러 개인 경우 (`|` 구분) 사용자 정답과 교집합이 있으면 정답 처리
- `Subjective`(주관식): 모든 공백 문자를 제거한 뒤 `ToUpperInvariant` 비교
- `문항 파일명`은 수동 입력이 아닌 **앱 로컬 `QuestionSourceFiles` 디렉토리에서 읽은 PDF 파일 목록**에서 선택되며,
  정답 맵 반영 시 해당 파일명을 `SourceFileName`으로 사용한다.
- 연습은 기본적으로 모든 문항을 출제하되, `정답 없는 문항만 제외` 토글로 제어

## 5. 계층 구조(예정)
- Presentation
  - 페이지: 시작, 카테고리, 업로드, 연습, 오답노트
  - ViewModel: 상태 관리, 커맨드, 화면 바인딩
- Domain
  - 채점 규칙, 정답 비교 정책, 랜덤 출제 규칙
- Infrastructure
  - 정답맵 파서, OCR 어댑터, 로컬 저장소 레포지토리(JSON)
  - JSON 손상 파일 백업 및 재초기화
- Application
  - 워크플로우 오케스트레이션

## 6. 주요 흐름
1. PDF 업로드
   - 사용자가 PDF 업로드 -> OCR 분석 실행 -> 문항 후보 분할 -> OCR 페이지 텍스트/이미지/진단 저장
2. 정답 매핑
   - 정답 맵 텍스트 파싱 -> `(문항번호, 정답 목록)` 생성
   - 문제/정답 매핑 후 로컬 저장
3. 연습 시작
   - 카테고리에서 문항 선택 수 입력 -> 랜덤으로 문제 추출
   - 입력을 채점하고 오답 상태 저장 완료 -> 현재 문항에 정오답 표시 -> 사용자가 다음 문항으로 이동
4. 종료
   - 정답 수 집계 후 화면 표시
5. 오답 노트
   - 정답 실패 항목 저장
   - 재학습 시 정답이면 삭제

## 7. 개발 우선순위
- 1단계: MVVM 구조 완성 및 카테고리/문항 도메인 모델 정리
- 2단계: OCR 문항 분할 정확도 개선 및 샘플 PDF별 진단 축적
- 3단계: 로컬 저장소 안정화(JSON 백업/마이그레이션, SQLite 전환 검토)
- 4단계: 모바일 OCR 배포 경로 확정 및 플랫폼별 실행 검증
- 5단계: UI 품질 개선 및 사용성 보완

## 8. 미확정/확실하지 않은 항목
- PDF 문제 분리 규칙은 기출별로 형식이 달라, 자동 분할 정확도는 확정 불가
- 스캔본/이미지 잡음이 큰 경우 실패 판정 기준(예: 최소 신뢰도 임계값)은 추후 실데이터 기반으로 조정 필요

## 9. PDF 샘플 분석 메모(진행 중)
- 현재 `src/` 폴더에서 추가된 여러 기출 PDF를 단순 텍스트 디코딩/패턴 스캔 기준으로 확인했습니다.
- `문항 분할`은 현재 문항 헤더 가설 전체를 수집한 뒤 문서 수준의 최적 번호 경로와 구조 모호성 진단을 계산하는 방식입니다.
  - 적용 패턴: `문항 n`, `n.`, `n)`, `n번`, `(n)`, `①` 계열, `가.`, `A.` 등
  - 숫자 선택지, 수량 표현, 페이지 번호는 실제 문항 헤더와 좌표·문맥·연속 번호 경로를 비교해 제외합니다.
  - 이미지 영역은 페이지·열별 의미 경계를 분할 결과에 함께 기록하며 OCR이 인식하지 못한 비문자 콘텐츠를 글자 bbox로 잘라내지 않습니다.
  - 분할 실패 파일은 분석 결과에서 후보 수가 0으로 노출되어 사용자 확인 필요 상태로 표시됩니다.
- 다음 단계: 실제 OCR 좌표(행/단어 박스) 기반 또는 품질별 규칙 가중치 조합으로 정밀 분할 정확도를 올릴 계획입니다.
